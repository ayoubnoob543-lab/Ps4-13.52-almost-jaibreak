# External source notes — focused patch_mount / FFS investigation

## OSM-Made/PS4-Kernel-SDK

Repository: https://github.com/OSM-Made/PS4-Kernel-SDK
README: describes a work-in-progress PS4 kernel SDK that generates C headers from YAML offset files; it says offsets should be updated from a known-good kernel dump and tested on hardware, but this is a project guideline, not proof that every present entry was sourced that way.
13.02 YAML: https://github.com/OSM-Made/PS4-Kernel-SDK/blob/e843f6fbd19f67d7e124426c61826d9925b94a55/offsets/firmware-1302.yaml
Initial 13.02 commit: https://github.com/OSM-Made/PS4-Kernel-SDK/commit/093808ee1563dfdb735b69ba2bfc925a9439ff54
Initial commit metadata: OSM-Made, 2026-01-22, “Add 13.02 offsets”, one file changed, 853 lines added.
File history includes subsequent additions of functions, Fusion hooks, fatal traps, delay, and PRX path patch; no FFS function or dump was observed.
The YAML contains patch_mount=0x001512A7, M_MOUNT=0x01A40250, getnewvnode=0x0036E2F0, vn_fullpath=0x00308CE0, kern_open=0x003435E0, malloc=0x00009520, free=0x000096E0, kmem_alloc=0x00465A50, kmem_free=0x00465C20. It contains no ffs_mountfs, ffs_reload, ffs_vget, ffs_alloc, UFS strings, struct fs, or fs_ncg/fs_cssize/fs_contigsumsize/fs_bsize/fs_fsize fields.
Its file tree has YAML offsets, generator code, headers, loader, samples; no kernel.bin/ELF/dump/image was found.

## Comparison

A local parser comparing Fusion and OSM YAML found 163 common names, 162 identical common offsets, and one difference: `trap_fatalHook` is 0 in Fusion but 0x0014AA90 in OSM. Target mount/VFS/allocator offsets are identical across the two. OSM’s 13.02 commit occurred after Fusion’s 13.02 PR/commit and does not expose a separate primary source in the commit page; this supports `DERIVED`/same-lineage classification, not independence proof.

Local kpayload 13.02/13.04 has `mountpfs__sceSblPfsSetKeys_hook1`, `mountpfs__sceSblPfsSetKeys_hook2`, `enable_data_mount_patch`, `malloc`, `free`, PFS and VM offsets. It has no `patch_mount`, `ffs_mountfs`, `ffs_reload`, `struct fs`, or UFS fields. Selected values are identical in the local 13.02 and 13.04 tables.

## kpayload / upstream sources

SiSTR0/ps4-hen-vtx patch.c: https://github.com/SiSTR0/ps4-hen-vtx/blob/master/kpayload/source/patch.c
This source uses `enable_data_mount_patch` to patch SceShellCore process memory and describes enabling remote package installation; this is not an FFS kernel mount function.

stooged/ps4-hen-VR-505 fpkg.c: https://github.com/stooged/ps4-hen-VR-505/blob/master/kpayload/source/fpkg.c
This source uses `mountpfs__sceSblPfsSetKeys_hook1/2` around `sceSblPfsSetKeys`, showing the name is PFS/key-management related, not UFS `ffs_mountfs`.

TeamFAPS/PS4-Offsets: https://github.com/TeamFAPS/PS4-Offsets/blob/master/readme.md
Older offset documentation labels `mountpfs__sceSblPfsSetKeys_hook1/2` under Fpkg hooks. This is useful lineage for the PFS name and argues against treating it as FFS.

## Celsius documentation

adri scanner: https://github.com/adri22235/ps4-suid-scanner
1304.c: https://github.com/adri22235/ps4-suid-scanner/blob/main/1304.c
The repo documents Celsius/ffs_mountfs and says it works up to 13.04, but provides no Orbis kernel body, dump, or FFS disassembly. Its 13.04 offsets are described as based on 13.02 and “identical kernel” plus Pharaoh2k verification. This is `SOURCE_ONLY`; it does not establish FFS correspondence.

## Classification

- `patch_mount` in Fusion/OSM: `SOURCE_ONLY` for a published label/offset; `HYPOTHESIS` as a possible generic mount-related patch; `INVALID` as proof of `ffs_mountfs` or Celsius.
- `M_MOUNT`, `getnewvnode`, `vn_fullpath`, `kern_open`: `CORROBORATED` as published VFS-like/general symbols; not FFS-specific.
- `mountpfs__sceSblPfsSetKeys_hook*`, `enable_data_mount_patch`: `CORROBORATED` as PFS/SceShellCore package/mount infrastructure; `INVALID` as `ffs_mountfs`.
- FreeBSD `ffs_mountfs`/`ffs_reload` source and `fs_*` fields: `VERIFIED` for FreeBSD upstream reference only; `INVALID` as direct Orbis evidence.
- Celsius in Orbis 13.02: `SOURCE_ONLY`/`HYPOTHESIS`/`UNVERIFIED`; no additional direct evidence found.

## Current conclusion

No public artifact currently supplies enough information to identify the 13.02 route `mount -> UFS/FFS -> ffs_mountfs`. The next most informative artifact is a legitimate 13.02 Orbis disassembly window around 0x1512A7 with provenance/hash, or a primary bollars artifact that gives a function signature/offset and the exact UFS image or kernel analysis supporting Celsius.
